# Relay Charter: M3 Static-First Cloudflare Migration

## Identity

- Relay: `m3-static-cloudflare`
- Root: `.pi-web/relays/m3-static-cloudflare/`
- Upgrade sequence: third of four milestone Relays

## Goal and finish line

Complete M3 from `docs/UPGRADE_HARNESS_PLAN.md` after M2 is green. The Relay is complete only when:

1. Historical years, places, and processed border payloads are generated by a controlled refresh workflow into pinned immutable static artifacts preserving the existing client contract.
2. Deployment builds use only pinned local/immutable inputs and make no GitHub or PASDA requests.
3. Historical map views and school-district views invoke no runtime compute for page HTML or data assets.
4. Year routes are fully enumerated static outputs; unknown years use a useful static 404; sitemap and crawler files are static and validated.
5. Remaining Next API routes are removed from the static app. Feedback is isolated as one bounded Cloudflare Function/Worker; Wikipedia is direct browser access or one exactly routed, tightly cached Worker only if deterministic tests prove it necessary.
6. Cloudflare static headers, redirects/routes, deployment configuration, secrets documentation, bot/AI-crawler controls, quota verification steps, and rollback instructions are present and portable where possible.
7. A local/static preview proves deep links, BC years, maps, feedback failure behavior, and approved dynamic routing.
8. A Cloudflare preview deployment is verified: normal pages/data are static asset hits, and only approved dynamic paths invoke Worker quota.
9. No broad Worker route can intercept ordinary page or asset traffic.
10. `yarn validate`, static-export validation, and documented quota checks pass.

The M3 section and approved architecture in `docs/UPGRADE_HARNESS_PLAN.md`, plus `AGENTS.md`, are designated supporting requirements. Changing this finish line requires owner agreement.

## Leg sizing

One runner owns the entire M3 milestone, except that the required account-access intervention may pause it. Resume as the next numbered leg after the owner performs the documented account step.

## Task selection

Choose the highest-priority unblocked item, preferring local static conversion and route isolation before provider configuration. Do all account-independent work before raising an access intervention. Do not begin M4 optimization.

## Handover

After M3 is fully green, update status/log and spawn exactly one M4 session:

```text
Relay "m4-optimize-launch" leg 1 begins now.

You are the next runner in this Relay method chain.

Read:
- .pi-web/relays/m4-optimize-launch/charter.md
- .pi-web/relays/m4-optimize-launch/status.md

Do not read log.md end-to-end. Use it only for targeted lookup if status.md or charter.md points you there.

Run one leg according to the charter. Before finishing, update status.md, append log.md, make work durable, then stop complete or stop with a clear intervention note.
```

Never spawn early or more than once. Stop without spawning on intervention.

## Intervention signal

Stop with `BLOCKED — OWNER INPUT REQUIRED` for finish-line/scope changes, any paid-service risk, any account/secret/DNS/production access step, or subjective user-facing behavior. For account access, first finish all safe local work and write exact non-secret owner instructions. Never request credentials in chat.

## Reading discipline

Read charter, status, `AGENTS.md`, the exact M3 plan/architecture sections, and only referenced/implicated files. Do not defensively read full logs, backlog, or repository. Repair the baton when possible; stop on subjective ambiguity.
